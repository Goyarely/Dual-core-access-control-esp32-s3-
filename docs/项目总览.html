双核智能门禁系统

ESP32-S3 负责「看与说」——摄像头人脸识别、屏幕交互、云端上报；GD32F303ZE 负责「做与守」——协议校验、继电器开锁、密码备用、看门狗与掉电日志。两板经一根 UART 组成异构双核门禁终端，两周内交付可演示、可量化、可写进简历的完整闭环。

端侧人脸识别（离线）动作挑战活体 UART 二进制帧协议MQTT 只上不下 LVGL 9.5 中文 UI独立看门狗
视觉主控 ESP32-S3-WROOM N16R8 执行主控 GD32F303ZET6（120MHz M4F） 链路 UART1 115200 · IO10/11 ↔ PA2/PA3 工期 14 天

01整体思路

判决与执行分离：ESP32 是「大脑」（判决），GD32 是「手 + 保险丝」（执行与否决）。两板互不信任、只认协议帧——这条边界本身就是本方案的安全叙事。

ESP32-S3 · 看 · 说 · 想

感知 / 交互 / 云

  • GC0308 采集 + 人脸检测（MSR+MNP，40ms/帧）+ 识别（mfn_s8，512 维 embedding）
  • 动作挑战活体：随机提示转头/靠近，用连续帧人脸框位移判定，防静态照片
  • LVGL 界面 + 触摸轮询（FT6336，写 G_MODE=0 释放 IO10）
  • MQTT 上行上报 EMQX + Web 看板（只上不下，不订阅任何开锁主题）
GD32F303ZE · 动 · 守 · 查

执行 / 守护 / 备用认证

  • 帧解析 + CRC16 + HMAC 校验 + 时间戳/nonce 新鲜度 → 门禁状态机
  • 继电器开锁 2s + 超时强制断开；蜂鸣器 / LED 本地反馈
  • KEY1–4 四位密码（板载按键）作为人脸失败降级路径
  • 独立看门狗守护 + AT24C02 环形日志（掉电不丢，最近 64 条 × 4B）

为什么这么分 —— 三条硬理由

算力

推理只能跑在 S3 上

240MHz 双核 + 8MB Octal PSRAM + esp-dl；GD32 的 120MHz M4F 做不动神经网络推理。感知必须归 ESP32。

引脚账

GPIO 被吃光，只剩 IO10/IO11

摄像头占 12 脚（PWDN 在扩展器上）+ LCD 4 脚 + SD/I2C，执行侧要的继电器、按键、蜂鸣器无脚可接；GD32 有 6 个空闲脚 + 板载外设，天然匹配。

可靠性分离

锁的正确性不押在最复杂的板子上

ESP32 死机 / OTA 重启 / WiFi 崩溃时，GD32 裸机状态机 + 独立看门狗保证锁处于安全状态、日志照写。执行侧越简单越可靠，所以刻意不开 RTOS。

一次完整开锁的数据流

① 刷脸摄像头 20fps → 检测稳定 3 帧 → 识别 + 活体挑战
② 判决ESP32 face_engine 给出 face_id + similarity + liveness
③ 请求UART 发 UNLOCK_REQ（时间戳 + nonce + HMAC）
④ 校验GD32 验帧 + 验签 + 新鲜度（±5s），任一不过即拒绝
⑤ 执行继电器吸合 2s → 回 ACK → 双方记日志，ESP32 发 MQTT
评审修正已并入本方案（P0）：帧尾新增 4 字节 HMAC（防伪造，不只是防重放）；心跳帧携带 epoch 时间同步（GD32 无绝对时间来源）；锁型与失效语义必须二选一写死——磁力锁断电开（消防优先）或电插锁断电锁死（安防优先），状态机每个异常分支都要落这个语义。

02系统结构

两板各跑各的固件，唯一的耦合点是 UART 帧协议。ESP32 侧五任务双核分工，GD32 侧裸机主循环。

ESP32 侧任务（xTaskCreatePinnedToCore）

任务核优先级频率
camera_task1520fps 采集
face_task14检测 15fps · 稳定后触发识别
link_task04事件驱动（UART 事件队列）
ui_task03LVGL 30fps（预览用 lv_canvas 拷贝）
net_task02事件驱动（MQTT 上报）

GD32 侧主循环（裸机）

  • USART1 RX 中断 → 环形缓冲，主循环逐字节解析状态机（找帧头 → 收满 → 验 CRC/HMAC）
  • 1ms SysTick 时基：开锁 2s 计时、锁定 60s 倒计时、心跳超时（1s × 3 次丢 → 链路故障灯）
  • 独立看门狗 FWDGT 喂狗点：主循环 + 收帧后，卡死自动复位，锁侧保持安全态
  • AT24C02（I2C0）：环形日志 64 条 × 4B（user_id + 事件 + 时间偏移），写前读尾指针
  • 发送侧同样带 ACK/重传（100ms 超时 × 3），与 ESP32 对等

05双板协议（两板逐字节一致）

小端 · CRC-16/MODBUS 覆盖 ver..payload · 发送侧待确认队列深度 8 + 100ms 超时 × 3 重传 · 接收侧 seq 窗口去重 · 心跳 1s（携带 epoch 供 GD32 同步时间）。

AA 55magic 2B
01ver 1B
type1B
seq1B
len1B ≤64
payload0–64B（UNLOCK_REQ：timestamp4 + nonce4 + reason1）
CRC162B MODBUS
HMAC324B 截断（评审新增）
type命令方向payload 摘要
1心跳 HEARTBEAT双向epoch(uint32) + 状态位
2ACK双向被确认帧的 seq
3开锁请求 UNLOCK_REQESP32 → GD32时间戳 + nonce + 原因（人脸/密码/管理）
4开锁应答 UNLOCK_ACKGD32 → ESP32结果（成功/拒绝/防重放拒绝）+ 剩余尝试
5按键事件 KEY_EVTGD32 → ESP32键值 + 按下/释放（UI 同步显示 * 号）
6状态查询 STATE双向门状态 / 锁定剩余 / 日志水位
新鲜度校验（P0-2 已修）：GD32 无绝对时间，本地时间基准来自心跳帧的 epoch，每次心跳同步一次；校验 |now − timestamp| < 5s 且 nonce 未用过（内存保留最近 16 个 nonce）。HMAC 密钥编译期烧入两板（同一 32 字节常量），没有它任何人都能伪造"新鲜"帧——CRC 只保完整性，不保真实性。
