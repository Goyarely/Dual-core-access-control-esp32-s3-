# 架构说明

## 一、总体结构

```
┌─────────────────────────────────┐        ┌──────────────────────────────┐
│  ESP32-S3（智能层）              │ UART1  │  GD32F303ZE（判决/执行层）     │
│                                 │115200  │                              │
│  GC0308 摄像头 → 人脸检测/识别    │ IO10──→│  USART1 收帧 → CRC/MAC 校验   │
│  LVGL UI（八界面状态机）          │ ←──IO11│  时间戳/nonce/失败次数/锁定    │
│  触摸（FT6336）                  │        │      ↓ 全过                   │
│  WiFi → HTTP 上报               │        │  PC0 → 光耦 → 继电器吸合 2s    │
│  触屏密码（管理员/开锁备用）       │        │      ↓ 拒绝回 REPLAY/DENIED/  │
└──────────────┬──────────────────┘        │      LOCKED                  │
               │ HTTP POST                 └───────┬──────────┬───────────┘
               ↓                                   │          │
┌──────────────────────────┐              AT24C02 掉电   FWDGT 看门狗
│  PC 后端（Python 标准库）  │              保持（防拔电   8s（防卡死）
│  SQLite + 网页            │              绕过锁定）      复位即锁定
└──────────────────────────┘
```

**为什么是双核**：门禁系统里"能不能开门"必须是独立的决定。
ESP32 被刷成恶意固件、固件有 bug、被拔掉——GD32 依然按规则拒绝开门（fail-secure）。
单板方案里，这三种情况都直接等于门被打开。

## 三、帧协议（两板同源 `link_proto.c`）

```
AA 55 │ ver │ type │ seq │ len │ payload(0~64B) │ CRC16 │ MAC32
 2B    1B    1B     1B    1B                   2B      4B    （小端）
```

- **CRC16/MODBUS**（初值 0xFFFF，多项式 0xA001）覆盖 ver..payload——只管传输完整性
- **MAC32**（SipHash-2-4，16 字节共享密钥，64 位输出折叠为 32 位）覆盖 ver..CRC——防伪造；
  改 CRC 本身也会被 MAC 抓到
  - 选型说明：总览原方案是 HMAC-SHA256 截断 4 字节，但 GD32 无加密库、需额外移植
    SHA256；SipHash-2-4 是短消息认证的标准算法，60 行可移植 C，安全性等价
- **seq**：每帧 +1，用于 ACK 与重传（100ms × 3 次）
- **消息类型**：1 心跳（epoch+状态）/ 2 ACK / 3 开锁请求 / 4 开锁应答 / 5 按键事件 / 6 状态

ACK 策略：收到任何非 ACK 帧必须回 ACK；开锁请求重传同一逻辑请求时换新 seq。
**注意**：不要用 seq 给开锁请求去重（seq 是所有帧共用的计数器，窗口会误判，
实测导致偶发"链路无应答"）——重放保护由时间戳 + nonce 承担。

## 四、安全模型

### 4.1 防伪造：MAC32

两板烧同一 16 字节密钥。攻击者没有密钥，即使算出合法 CRC 也过不了 MAC
（SipHash 官方向量验证过实现：空串 `0x726fdb47dd0e0e31` 等）。

### 4.2 防重放：时间戳 + nonce（GD32 状态机）

- ESP32 心跳携带 epoch（时间基准），开锁请求携带 timestamp + nonce
- GD32 校验：`|peer_epoch − timestamp| ≤ 5s`，且 nonce 未在最近 16 个里出现过
- 两者任一不过 → 回 `REPLAY`，计一次失败

### 4.3 防爆破：失败计数 + 锁定

- 连续 5 次被拒（可配置 1~10）→ 锁定 60 秒（可配置 10~300）
- 锁定期间**一切开锁请求**（含刷脸、密码）都回 `LOCKED`
- 状态存 **AT24C02**：拔电重启，锁定剩余时间和失败次数原样恢复

### 4.4 可用性：本地凭据 + 看门狗 + 故障指示

- 触屏密码开锁：ESP32 死机时门禁仍可由管理员开门（发 `reason=password` 请求）
- FWDGT 独立看门狗 8 秒：主循环卡死 → 复位 → 恢复锁定态（实测 7.6s）
- LED3（PF6）：ESP32 离线 3 秒 → 常亮

### 4.5 已知局限（如实记录）

- 单目 RGB 摄像头做不了无感（静默）活体；动作活体（转头挑战）已实现但
  默认关闭（`LIVENESS_ENABLE 0`）——照片攻击在当前版本是可用手段，
  真实产品需红外/结构光或专用活体算法
- 管理员密码是编译期常量（`ADMIN_PASSWORD "1234"`），改密码需重新编译；
  正确做法是存 NVS/EEPROM，交付前未做（见 test-report 的遗留项）
- MAC 密钥硬编码在源码里；量产应每台设备独立密钥并在配网时注入

## 五、数据流

### 5.1 通行记录上报

```
识别/密码 → 结果 → net_report_push(mid, 文字, 结果, 方式, 相似度)
                  → FreeRTOS 队列（8 条）→ 上报任务
                  → HTTP POST /api/record（失败重试 3 次，队满丢弃）
                  → SQLite records 表 → 网页（5s 自动刷新）
```

原则：**网络是旁路**。WiFi 未连接、上报失败都绝不阻塞识别与开锁。

### 5.2 人员姓名同步（版本号轮询）

```
网页改名 → POST /api/member → members_ver + 1
ESP32 每 10s GET /api/members/version（约 20 字节）
  版本变化 → 全量 GET /api/members → 更新本地 mid→姓名缓存
下一次刷脸 → 屏幕与记录即使用新姓名
```

设备侧不存姓名（触屏打不了中文）；姓名的唯一来源是后端人员表。

## 七、状态机

### ESP32 UI（`main/ui/ui_main.c`）

```
STANDBY ──稳定 3 帧──→ [活体（默认关）] ──→ SCANNING ──识别──→ SUCCESS(3s)/DENIED(3s)
   ↑                                                                │
   └──────────────────── 必须先离开画面（防界面闪烁）←───────────────┘
STANDBY ──长按 1.5s──→ AUTH(管理员) ──密码──→ MENU ──→ MEMBERS/DELETE/SETTINGS/ENROLLING
STANDBY ──「密码」按钮──→ AUTH(开锁) ──密码──→ SUCCESS（发 reason=password 请求）
任意 ──连续失败达上限──→ LOCKOUT(倒计时) ──→ STANDBY
```

### GD32 门禁 FSM（`App/door_fsm.c`）

```
LOCKED ──通过全部校验──→ UNLOCKED（继电器 2s，SysTick 计时）──→ LOCKED
   │                        │
   │ 失败 5 次              │
   ↓                        │
LOCKOUT（60s，EEPROM 记剩余秒数）──到期──→ LOCKED
LOCKOUT 期间：一切请求回 LOCKED（刷脸/密码/重放全拒）
```
